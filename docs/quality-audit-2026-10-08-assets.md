## 优先处理的五项问题

### 1. 同一人物的别名会形成两个独立身份，现有项目已出现跨集造型漂移

**类别：当前数据缺陷 + 可复现的代码缺口；优先级 P1。**

证据：资产 92 为“维克多·凯恩”，描述为深色短发、鬓角微灰；资产 123 为“维克多”，描述明确写“全名维克多·凯恩”，却改为灰金色短发。两者 `assetsId=null`，各自拥有不同人物板；前者关联 29 集，后者关联 37–58 集。这是同一反派被建成不同身份。资产 124“艾娃父亲”和 169“父亲”也没有共同身份或衍生链接；年轻照片和中年录像可以合理用不同状态呈现，但现在没有父身份继承保证。

代码：

- `D:\Toonflow-app-master\src\utils\scriptAssetExtraction.ts:79` 只在循环前读取一次旧资产。
- `...\scriptAssetExtraction.ts:94` 每个剧本批次都传同一份初始 `existingAssets`，没有把本轮前面发现的人物送给后续批次。
- `...\scriptAssetExtraction.ts:81`、`:109` 去重实际依赖 `type + name.trim()`；同义姓名只在提示词 `:93` 中要求复用，没有实体归一化约束。

内存复现：两集依次返回 Victor Kane / Victor，第二批 `existingAssets` 仍为空，最终确实创建两个父资产。这里没有调用真实 AI，说明程序无法消解模型返回的别名；不能据此断言现存重复一定由本版本首次制造。

影响：后续分镜和 H3 选到了不同资产 ID 时，提示词都可以“正确引用”，画面却已经换人或换发色。增加图片质量标签无法修复这个问题。

建议：先生成全剧角色身份目录，保存规范名、别名、关系和稳定 identityId；后续批次引用已有目录，状态资产只能挂在同一身份下。先人工核对现有维克多两份身份的保留方案，再重建关联；保留旧图和已完成视频，不能直接删图或重做整剧。

验证：用全名/简称/关系称谓混合的三集样本，应只形成一个父身份，多个年龄或衣装状态拥有明确父链接；真实相邻剧集的资产引用与人物板同时检查。

### 2. 资产库和生产流程使用不同人物生成链路，同一个项目难以稳定复现

**类别：确定的入口分歧；优先级 P1。**

代码：

- `D:\Toonflow-app-master\src\utils\assetImageModel.ts:6`–`:17` 对所有 `role` 忽略请求模型，固定返回 Qwen 独立四视图模型；普通人物生成在 `src\routes\assetsGenerate\generateAssets.ts:39` 和批量路由 `:55` 使用此解析器。
- `D:\Toonflow-app-master\src\routes\production\assets\batchGenerateAssetsImage.ts:145`–`:156` 则直接使用项目图片模型、固定 `16:9`、把父资产整张选图作为参考，并不走模型解析器或独立四视图工作流。
- 生产路由 `:169`–`:175` 不分析结果内容，就把人物结果标为 `four_view`、`ready`。

真实数据支持入口差异：基础人物是独立四视图模型，艾娃雨夜/水下/清晨衍生态用普通 Qwen 图生图模型。这不是单凭文档推测。

影响：用户在不同页面生成同一资产，会得到不同画幅、不同视角生成方式和不同参考图语义。资产库模型选择在人物类型上还会被隐藏地覆盖。整板图生图需要同时处理四人外观、衣装变化、布局和状态，独立四视图则先决定正面再旋转；两种难度与失败模式不同。

建议：把人物生成整理成一套共享流程：解析有效模型 → 读取父身份/目标状态 → 生成目标态正面锚点 → 派生其他视角 → 拼板 → 完整性检查 → 写入候选与选图。若人物只允许专用四视图模型，界面直接说明并显示实际模型；若保留用户选择，则后端按模型能力执行。

验证：通过资产库单张、资产库批量、生产自动生成三个入口生成相同描述时，比较有效模型、目标态正面、参考图角色、画幅和保存元数据，结果契约应一致；不要求随机图像逐像素相同。

### 3. 四视图“父身份参考”与“已确认目标态正面锚点”的语义混用，会把新状态提示词彻底丢掉

**类别：条件触发的确定缺陷；优先级 P1。**

四视图供应商自身声明第一张图必须是“当前目标状态的正面全身锚点”（`D:\Toonflow-app-master\data\vendor\comfyui_qwen21_fourview.ts:17`）。但生成路由只要求衍生人物传“同一角色的已确认参考图”（`src\routes\assetsGenerate\generateAssets.ts:45`–`:48`），没有区分父身份、旧状态和已完成目标态。

供应商 `:148`–`:155`：一旦传参考图，直接将 `LoadImage` 当作新板的正面，不生成新的正面。`:117` 只有 `view === front` 才放入当前资产 facts，而有参考图时 front 编码节点不存在。因此 portrait/side/back 的请求只写“保留参考人的衣装、状态、画风”，没有本次换装、湿身、受伤或新画风内容。

无生成复现：给图构造函数传 `old_front.png`，提示词加入唯一目标 `TARGET_NEW_STATE_RED_COAT_3D`；构造图中 `hasFrontRender=false`，所有 `TextEncodeQwenImage21` 的 prompt 均没有该目标。即使文案写了新红外套，模型也收不到新红外套。

边界：如果调用者确实提供已经正确的目标态单人正面图，此流程是合理的视角扩展；缺陷发生于把父图/旧图当普通参考来修改外观的调用。不能把供应商在正确输入合同时的旋转设计也称为失败。

建议：明确拆分 `identityReference`、`currentStateFrontAnchor`。使用父身份或旧图时先执行带目标 facts 的正面编辑；只有已确认目标态正面才允许跳过此步骤。检查输入是否单人正面全身，完整展示板不能直接冒充 front 锚点。

验证：父角色工装 → 目标睡衣、干衣 → 湿衣、旧画风 → 新画风三种修改，各自新正面编码必须收到目标变化；只有明确选择“仅扩视角”时才能不重生成正面。

### 4. 首次正面设计没有可达的视觉画风参考，风格很难从文字变成稳定图像

**类别：确定的能力缺口 + 视觉质量设计缺口；优先级 P1。**

证据：

- `D:\Toonflow-app-master\src\routes\assetsGenerate\generateAssets.ts:43` 和批量 `batchGenerateImageAssets.ts:59` 禁止没有第一张人物锚点时传第二张风格图。
- `D:\Toonflow-app-master\data\vendor\comfyui_qwen21_fourview.ts:151` 首次正面调用 `characterPrompt(facts, front, false)`；第二风格图只在 `:157`–`:160` 送给 portrait/side/back。
- `D:\Toonflow-app-master\Toonflow-web-master\src\views\assets\components\generateImage.vue:232`–`:240` 实际 UI 请求没有 `styleBase64`。
- 图片提示词的视觉参考只有父图/当前图：`src\utils\assetPromptGeneration.ts:38`–`:41`。项目画风手册是文字，当前管线没有统一风格板流入首次正面与场景图的路径。

影响：即使后端存在“可选风格图”，它不能决定第一次正面锚点，后续又被要求保留该正面的媒介、衣装和布光。实际三张角色的动画脸程度不同，公寓接近摄影环境，说明当前文字锚点没有形成足够稳定的统一视觉系统。不能从这里证明模型能力不足，也不能保证简单加入一张示例就解决美感。

建议：选定一个明确项目美术方向，先制作少量受控样本：成年女性、成年男性、室内、灾变外景，确认面部抽象程度、材质、色彩与布光。身份图和风格图分开传；风格图要参与第一次正面与场景主图，不能把示例人物外貌作为身份继承。把正面候选确认作为四视图扩展前的实际检查点，可以沿用快速自动采用，但必须让用户知道它是候选且容易替换。

验证：保持同一身份/场景事实，固定随机种子和采样设置，仅调整美术锚点，做同屏 A/B；检查五官美感、风格统一和服装事实，而不是仅看“生成成功”。

### 5. `4K` 选择没有对应 4K 单画面，2K 和 4K 在普通 Qwen 上完全相同

**类别：确定的规格/精度问题；优先级 P2。**

- `D:\Toonflow-app-master\data\vendor\comfyui_local.ts:152`：1K 最长边 1024，其他质量一律 2048；2K 和 4K 图相同。主项目的公寓图实际为 2048×1152。
- `D:\Toonflow-app-master\data\vendor\comfyui_qwen21_fourview.ts:131`：4K 每个视角 1024×1536，2K 896×1344，1K 640×960。拼成很宽的板并不代表每个身体/面部达到 4K。无生成构造图复现的拼板为 4102×1536（含 6 像素间距）。
- 现有基础人物板有 5008×1888 历史文件，说明旧工作流输出还可能不同；不能把当前配置推导的 4102×1536说成历史板的生成尺寸。

影响：用户以为提高到 4K 会增加细节，实际普通 Qwen 没有任何变化；人物四栏整体宽度掩盖了每个视角有效分辨率，后续视频继续缩小整板时脸部辨识度更弱。像素大小只是清晰度因素，不等于审美质量。

建议：界面区分“整板尺寸”和“每视角尺寸”，显示真实输出；普通 Qwen 真正支持 4K 时才提供该选项，或者明确改名为标准/高质量并列出尺寸。若考虑超分，单独记录原生渲染与超分规格，避免夸大细节恢复。

验证：同一输入选择 1K/2K/4K，查看构造图与最终图片 metadata，报告真实尺寸；同时比较脸部有效像素和视频端缩放后的可辨识度。

## 其他优化点与风险边界

### 成图审核没有进入生产，现有测试明确把直接采用设为期望行为

`D:\Toonflow-app-master\src\utils\assetPromptGeneration.ts:168` 存在 `reviewAssetImage`，生产 `src` 仅有这个定义，没有调用。普通单张/批量只检查解码与宽高比例，然后替换 `imageId`（`generateAssets.ts:84`–`:103`；`batchGenerateImageAssets.ts:102`–`:121`）。生产自动链直接标完成，没有成图视觉审核（`production/assets/batchGenerateAssetsImage.ts:168`–`:187`）。

这不是未经授权就应强加审批的依据：`tests/asset-image-review-routes.test.ts` 刻意断言 successful images are adopted without calling the image reviewer，测试对此通过。它是需要重新评估的质量策略。提示词审核通过并不能证明图片的脸、衣装、状态、画风真的符合要求。

建议把“文件可用”“内容符合”“用户选用”分成可观察状态。可先增加低成本自动检查和可回退候选，不必用昂贵多模态审核挡住每一次操作；高价值主角/主场景在大量分镜前先确认。保留已选图与候选历史。

### 美术手册和渲染参数没有纳入提示词/图片版本链

`D:\Toonflow-app-master\src\utils\assetDescriptionVersion.ts:24`–`:29` 只比较描述版本。改了项目画风、风格 Skill 或工作流也不改变这个判断。旧 prompt 仍可能被视为“当前版本”。Qwen 随机 seed 在图构造时生成（`comfyui_local.ts:163`；`comfyui_qwen21_fourview.ts:153`、`:162`），没有返回或保存到图片记录，`o_image` 本身也没有 seed、工作流版本、最终 runtime prompt、风格 Skill hash 字段。

建议保存 prompt、Skill、有效供应商配置与工作流的快照/hash，seed 和最终生成尺寸；只在相关事实变化时标明需要重做，不自动重生成旧图。这样才能判断改好的是模板、模型、采样参数，还是随机运气。

### 资产 Skill 仍教 H3 使用独立裁切，与现行整板引用规则矛盾

`D:\Toonflow-app-master\data\skills\asset_visual_design.md:41` 和 `data\skills\art_skills\realistic_3d_anime\art_prompt\art_character.md:26` 仍说 H3 按已保存独立裁切引用人物。该说法与当前“完整人物板占一个 Picture”的实际规则不一致。它不一定每次触发坏视频，但会把错误参考语义重新带回资产/导演提示词。

建议统一共用事实层对 H3 的描述；保留四栏作为资产展示/身份设计用途，视频上传 allocation 以现行整板政策为准。
